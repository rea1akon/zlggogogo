## 3. 部署 Worker 后端（独立 Worker）

Worker 与 Pages 是**两个独立资源**：Worker 提供 `/api/*`，Pages 只托管前端静态文件。

```bash
cd cloudflare

# ① 登录 Cloudflare（浏览器授权一次）
npx wrangler login

# ② 创建 D1 数据库，记下返回的 database_id（形如 UUID）
npm run db:create
#   等价于：npx wrangler d1 create zlg_maintenance_db

# ③ 把真实 database_id 填进 wrangler.toml 的【两处】：
#    - 顶层 [[d1_databases]] 的 database_id
#    - [env.production.d1_databases]] 的 database_id
#    （占位符目前是 00000000-0000-0000-0000-000000000000）

# ④ 对线上 D1 执行迁移（建表 + 种子）
npm run db:migrate:remote
#   等价于：npx wrangler d1 migrations apply zlg_maintenance_db --remote

# ⑤ 部署 Worker（用 production 环境，使 ALLOWED_ORIGINS 指向 Pages 域名）
npm run deploy:worker -- --env production
#   等价于：npx wrangler deploy --env production
```

部署成功后会得到 Worker 地址，形如：
```
https://zlg-maintenance-api.<你的子域>.workers.dev
```
记下它，第 4 步 Pages 需要填进 `VITE_API_BASE`。

> 本工程**不依赖任何密钥即可运行**：会话用 D1 表存储，`REQUIRE_AUTH` 是普通变量（默认 `true`），
> 无需 `wrangler secret put`。若日后接入 R2 / 短信网关等，才需要用 secret（见第 5 节）。

## 4. 部署 Pages 前端（连 Git 自动构建）

在 Cloudflare 控制台 **Workers & Pages → 创建 → Pages → 连接到 Git**：

| 配置项 | 值 |
|--------|-----|
| 仓库 | 选择第 2 步推送的 GitHub 仓库 |
| **Root directory（根目录）** | `cloudflare` |
| Build command（构建命令） | `npm run build` |
| Build output directory（输出目录） | `frontend/dist` |
| Node 版本 | 在 **设置 → 环境变量** 加 `NODE_VERSION = 20`（与 `.node-version` 一致） |

### Pages 环境变量（生产）

| 变量名 | 值 | 说明 |
|--------|-----|------|
| `VITE_API_BASE` | `https://zlg-maintenance-api.<你的子域>.workers.dev/api` | 前端调用的后端地址，**必须带 `/api` 后缀** |
| `NODE_VERSION` | `20` | 构建时使用的 Node 版本 |

> `VITE_API_BASE` 留空时前端走同源 `/api`（仅本地开发有效）。
> 上线后**必须**填 Worker 完整地址，否则页面能打开但所有接口 404。

保存后 Cloudflare 会拉取仓库、在 `cloudflare/` 下执行 `npm run build`，把 `frontend/dist` 发布。
每次 `git push` 到 `main` 都会自动重新构建部署。

### ⚠️ 还必须做一件事：让 Worker 允许 Pages 跨域

Worker 的 `ALLOWED_ORIGINS` 在生产环境（`wrangler.toml` 的 `[env.production.vars]`）目前是占位：
```
ALLOWED_ORIGINS = "https://zlg-maintenance.pages.dev"
```
把 `https://zlg-maintenance.pages.dev` 改成你实际的 **Pages 正式域名**（部署后控制台可见），
然后重新 `npm run deploy:worker -- --env production`，否则前端请求会被 CORS 拦截。

## 5. 敏感配置处理方式（必读）

| 场景 | 做法 |
|------|------|
| 本地密钥（如 `REQUIRE_AUTH`） | 写 `.dev.vars`，已在 `.gitignore` 中，绝不进 Git |
| 线上 Worker 密钥（R2/SMS 等） | `npx wrangler secret put <KEY>`，**不要**写进 `wrangler.toml` |
| 前端变量 | 仅 `VITE_` 前缀会被编译进产物，**严禁放任何密钥** |
| 数据库 | 永远用参数化查询（列名取自 `resources.js` 白名单），无拼接注入风险 |
| 账号口令 | 存储 `SHA-256(salt:password)`，`salt` 随机；线上改密见第 6 节 |

## 6. 上线后必做：修改默认口令

种子数据内置 `admin / zlg123`（仅用于本地联调）。上线前务必改密：

```bash
cd cloudflare
npm run hash-password -- 你的新密码
# 输出 salt 与 password_hash，然后：
npx wrangler d1 execute zlg_maintenance_db --remote --command \
  "UPDATE users SET salt='<salt>', password_hash='<hash>' WHERE username='admin'"
```

也可在前端登录后通过接口改，或直接用 `UPDATE` 语句重置任意账号。

## 8. 常见故障

| 现象 | 原因 / 解决 |
|------|------|
| Pages 打开但接口全 404 | `VITE_API_BASE` 没填或没带 `/api` 后缀 → 补上重部署 |
| 接口返回 CORS 错误 | Worker `ALLOWED_ORIGINS` 没包含 Pages 域名 → 改 `env.production.vars` 后重部署 Worker |
| Worker 部署报 database_id 无效 | `wrangler.toml` 两处还填着占位 `000...` → 填 `wrangler d1 create` 返回的真实 ID |
| 线上 D1 查询报错表不存在 | 只跑了本地迁移 → 补 `npm run db:migrate:remote` |
| 构建失败找不到 vite | Node 版本过低 → Pages 环境变量加 `NODE_VERSION=20` |
| 本地 `curl -d` 传中文被校验拒 | Git Bash 编码问题，**用 `--data-binary @file.json`** 传中文，Worker 本身正常 |
